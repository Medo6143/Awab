## Stack

React Native 0.81 (New Architecture, bridgeless), Expo SDK 54, TypeScript, Redux Toolkit with redux-persist, and hand-written Android code in Java and Kotlin for the adhan, alarms, battery helpers and the home-screen widget. Android only.

## Architecture in one paragraph

Three layers, dependencies pointing inward: `presentation → domain ← data`. `src/domain` holds entities, pure logic and the interfaces for anything with side effects (`QuranPlayer`, `AzanSound`, `LocationProvider`, `MosqueFinder`, `PrayerTimesSource`, `NotificationCenter`, …). `src/data` implements them on expo, native modules and HTTP, and `src/data/container.ts` is the one place that picks the concrete classes. Screens and hooks get them through `useDependencies()`, so a test can swap any of them for a fake with `DependencyProvider`. Some older code still imports `src/data` directly; [#24](https://github.com/Medo6143/Awab/issues/24) tracks moving it. Details in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Run it

Prerequisites: Node.js 18 or later, JDK 17, Android Studio with the Android SDK, and a phone or emulator.

```bash
git clone https://github.com/Medo6143/Awab.git
cd Awab
npm install
npx expo prebuild --platform android --no-install
```

Release APK for a phone connected over USB (arm64):

```bash
npm run apk:phone
```

Release APK for a running emulator (x86_64):

```bash
npm run apk:emu
```

Type check, which is the only automated check:

```bash
npx tsc --noEmit -p .
```

The landing page, the APK download and the `/api/mosques` function the nearest-mosque feature calls are all in `landing/`, deployed to Vercel at `owwab.vercel.app`:

```bash
cd landing && npx vercel --prod --yes
```

Notes:

- `android/` is generated by prebuild and is git-ignored. Native code lives in `native/android/` and is injected by `plugins/withOwwabNative.js`.
- An arm64 build does not start on the x86_64 emulator, and the reverse.
- The adhan, alarms and the floating tasbeeh should be tested on a real phone.
- With an emulator open, a release build and `tsc` can run out of memory (Gradle asks for a 4 GB heap). Close the emulator, or type-check with a smaller heap: `node --max-old-space-size=1200 node_modules/typescript/bin/tsc --noEmit -p .`

## Engineering notes

This section documents the hardest problems encountered and the reasoning behind each solution. These are real engineering trade-offs, not textbook answers.

---

### Challenge 1: Azan Reliability in Doze Mode

**The Problem:**
Android's Doze Mode and Battery Optimization aggressively suspend background processes, including `setTimeout`, `setInterval`, and `expo-notifications` scheduled triggers. In testing, expo-notifications-based Azans were delayed by up to 15 minutes when the phone was idle.

**The Approach Tried First (❌ Failed):**
`expo-notifications` with `scheduleNotificationAsync` — silently dropped in Doze Mode on Samsung and Xiaomi devices.

**The Solution (✅):**
A fully native implementation using Java:

```java
// AzanModule.java — called from JavaScript via the React Native bridge
alarmManager.setExactAndAllowWhileIdle(
    AlarmManager.RTC_WAKEUP,
    triggerTimeMs,
    pendingIntent // → fires AzanReceiver
);
```

`setExactAndAllowWhileIdle` is the **only Android API** guaranteed to fire at the exact time even during Doze. The `BroadcastReceiver` then starts a `ForegroundService` which plays the Azan audio using `MediaPlayer` with `USAGE_ALARM` audio attributes — ensuring it overrides silent/vibrate mode just like a system alarm.

On Android 12+, the app also requests `SCHEDULE_EXACT_ALARM` permission and guides the user to the system settings page if it hasn't been granted.

---

### Challenge 2: Floating Tasbeeh Bubble — Persistence & State Sync

**The Problem:**
The floating bubble is drawn at the system level using `SYSTEM_ALERT_WINDOW`. When the user closes the app (or Android kills it), the JavaScript bridge dies. The bubble's native service survives, but any counts tapped while the app is dead have no way to reach Redux.

**The Solution (✅):**
**Bidirectional dual-source state management:**
1. Every tap in the native bubble increments a counter in Android `SharedPreferences` immediately.
2. When the user re-opens the app, `FloatingTasbeehController` (a render-less component at the root) reads that count through `floatingSebha.getSavedCount()` and reconciles it with the Redux state. The rule is a pure function in `src/domain/services/FloatingSebha.ts`:

```typescript
export const reconcileCount = (nativeCount: number | null, appCount: number): CountReconciliation => {
  if (nativeCount === null || !Number.isFinite(nativeCount)) return { kind: 'push' };
  if (nativeCount > appCount) return { kind: 'add', amount: nativeCount - appCount };
  if (nativeCount === 0 && appCount > 0) return { kind: 'reset' };
  if (appCount > nativeCount) return { kind: 'push' };
  return { kind: 'none' };
};
```

`add` counts the taps made while the app was dead (and logs them as dhikr), `reset` keeps a reset done in the bubble, and `push` sends the app's count back to the bubble. Taps survive a force-kill or a restart.

### Challenge 3: React Native New Architecture (Bridgeless Mode) Compatibility

**The Problem:**
Migrating to React Native 0.81's New Architecture (bridgeless mode) broke `react-native-track-player`. The app would hang on the splash screen with a `TurboModule ParsingException` because several `@ReactMethod` functions in the library's native code had incorrect return-type signatures for the new bridge.

**The Solution (✅):**
Applied a `.patch` file via `patch-package` that corrected all offending `@ReactMethod` signatures in the library's Kotlin source to explicitly return `Unit` (void) — the format required by TurboModules. This approach avoids forking the library and keeps the patch auditable and reproducible across `npm install` runs.

**A second, silent break:** in bridgeless mode `reactNativeHost.reactInstanceManager.currentReactContext` is always `null`. The track player's `MusicService.emit()` used it, so every notification button (play, pause, stop) was dropped without an error, and `MainActivity` crashed when the adhan opened it. Both now take the context from `(application as ReactApplication).reactHost?.currentReactContext` first: in `patches/react-native-track-player+4.1.2.patch` and in the code `plugins/withOwwabNative.js` injects. Any native code added to this app has to do the same.

### Challenge 4: Floating Bubble System Overlay Permission Flow (Android 11+)

**The Problem:**
`Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM` and `Settings.ACTION_MANAGE_OVERLAY_PERMISSION` both redirect the user to system settings pages. There is no callback when the user returns. The app had no way to know if permission was actually granted.

**The Solution (✅):**
Using an `AppState` listener to detect when the app returns to the foreground, then re-checking permission programmatically (`src/presentation/hooks/useFloatingSebha.ts`):

```typescript
/** Waits until the user comes back from a system settings page (or 30 s pass). */
const waitForReturn = () => new Promise<void>((resolve) => {
  const sub = AppState.addEventListener('change', (s) => {
    if (s === 'active') { sub.remove(); setTimeout(resolve, 500); } // let system state settle
  });
  setTimeout(() => { sub.remove(); resolve(); }, 30000); // safety fallback
});

const ensurePermission = async () => {
  if (await floatingSebha.hasPermission()) return true;
  await floatingSebha.requestPermission(); // opens the system settings page
  await waitForReturn();
  return floatingSebha.hasPermission(); // re-check after returning
};
```

### Challenge 5: Finding the nearest mosque when the map server is blocked

**The Problem:**
Mosques come from OpenStreetMap through the Overpass API: free, no key, nothing tied to the user. But from many Egyptian networks every public Overpass server is unreachable or answers 406, even on its status page. The app's main audience could not get a single result.

**What is in place (⚠️ partly solved):**
A small Vercel function, `landing/api/mosques.js`, asks Overpass from outside the user's network: the app calls `owwab.vercel.app/api/mosques?lat=…&lon=…`. It tries two Overpass servers (9 s each), trims the answer to id, position and names, and lets the edge cache it for a day per point. If the function fails, the app falls back to Nominatim, the other OpenStreetMap service. That answer is thinner (a name search, at most 40 results, ranked by importance), so the app keeps it for an hour instead of a day.

**Still open:** Overpass has also answered 406 to requests from Vercel, so in practice the app often lands on the Nominatim fallback, which misses unnamed and small mosques. The data source (Google Places, or only opening Google Maps) is undecided; see [docs/features/nearest-mosque.md](docs/features/nearest-mosque.md) and #22.

Privacy holds: the position is rounded to about 100 m before it leaves the phone, nothing is stored or logged on the server, and distances are computed on the phone from the exact position.
